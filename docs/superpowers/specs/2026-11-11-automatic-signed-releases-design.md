# Automatic signed main releases

Pushes to `main` automatically build and publish GitHub Release packages with the existing macOS Apple Development identity. Build numbers and plain `vMAJOR.MINOR.PATCH` versions advance automatically, starting from build117/v0.3.6 after the existing build116/v0.3.5-custom.2. No new package, source archive, Release title, or version tag contains a custom suffix. Local packages never enter the publication path.

Keep the existing three-platform workflow, package validation, GitHub artifact transfer, release environment, and update signing keys. A preparation job reserves an annotated release tag containing its numeric build, selected plain version, source version/commit/hash, and workflow run identity. Allocate above both historical published builds and earlier reservations; failed builds may leave gaps, and retries of the same run reuse their reservation. Serialize release runs, allowing GitHub to coalesce pending pushes to the newest commit, and skip a superseded source before publishing so a delayed build cannot become the latest release. A manual run remains available without requiring number/tag inputs.

The annotation records allocations without modifying main or introducing a version-bump commit loop. Using only published releases would recycle failed allocations; using workflow run numbers would couple product ordering to an arbitrary workflow counter. The existing annotated Git tag API and current workflow token provide the persistent reservation without another state branch. The highest published/reserved version advances its patch number; a newer source-manifest version acts as a floor. Historical custom tags are read for migration, never generated again.

Pass the selected version explicitly as `OINK_PUBLIC_RELEASE_VERSION` to every builder, assembler, validator, and feed publisher. The shared identity loader validates a plain version at or above the source base, changing only the display version. Existing compilation already propagates display versions into Rust, Tauri, Swift, bundle metadata, Windows resources, and package receipts. The raw source/identity files and hashes stay fixed at the tagged commit. A reproducible local public build may explicitly set the version from release.json; an ordinary local build retains its existing default and never publishes. Source archives use `Oink-<version>-build<build>-source.tar.gz`.

macOS keeps Team `D765989V7S`, certificate `3A92F137F2E694DFB6F4AC3E6F9A901EC6B1B7AA`, and the existing Sparkle key. Automatic ARM builds use the previously successful Intel cross-compilation route; metadata continues to disclose that native ARM runtime checks are not run in CI. Only this run's three GitHub package artifacts are assembled and uploaded. Local packaging receives no uploader or automatic trigger.
